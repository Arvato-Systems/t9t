# Development Plan: OpenBao KV API Integration

## Overview

This document describes the development plan for integrating t9t with the [OpenBao](https://openbao.org/) KV (Key-Value) secrets engine. The integration enables selected users to have their passwords automatically synchronized to OpenBao when changed, and removed when the user is deleted.

OpenBao is an open-source fork of HashiCorp Vault, providing a secrets management API. The KV v2 API is used for this integration.

---

## Requirements Summary

1. **Configuration**: OpenBao URL and credentials are stored in `UplinkConfiguration` (identified by a dedicated key, e.g. `"openbao"`).
2. **User Flag**: Each user gets a new boolean field `syncPasswordToOpenBao` (a checkbox in the UI) indicating whether the user's password is relevant for OpenBao.
3. **Password Sync on Update**: When a password is set/changed for a flagged user, the new plaintext password is sent to OpenBao via the KV API.
4. **Password Removal on Delete**: When a flagged user is deleted, the corresponding password secret is deleted from OpenBao.
5. **Visible Sync Failures**: Any failure to sync (missing configuration, network outage, etc.) must be clearly surfaced to the operator as a UI popup. The sync result **must not** silently discard errors. However, sync failures **must not block** the underlying password change or user deletion — the main operation always succeeds.

---

## Architecture

### Affected Modules

| Module | Change |
|---|---|
| `t9t-auth-api` | Add `syncPasswordToOpenBao` boolean field to `UserDTO` (in `auth.bon`) |
| `t9t-auth-sapi` | New `IPasswordSyncService` interface + `PasswordSyncStatus` enum |
| `t9t-auth-be` | No-op fallback stub (`@Fallback`) for `IPasswordSyncService`; hook into `UserCrudRequestHandler` on hard DELETE |
| `t9t-auth-jpa` | DB migration for the new user column; update JPA entity; hook into password set/change flows |
| `t9t-auth-be-openbao` | **New Maven module**: OpenBao implementation of `IPasswordSyncService` |
| `t9t-zkui-screens` | Add `syncPasswordToOpenBao` checkbox to `user28.zul` |

### Integration Pattern

- A generic `IPasswordSyncService` interface is defined in **`t9t-auth-sapi`** (not in `t9t-base-be`). The interface is auth-specific by nature and has no reason to live in the base framework.
- The service is injected via JDP (dependency injection) in request handlers and auth-jpa services.
- The current `OpenBaoPasswordSyncService` implementation lives in the new **`t9t-auth-be-openbao`** Maven module, which is an optional runtime dependency. Future alternative implementations (e.g. HashiCorp Vault, AWS Secrets Manager) would each live in their own `t9t-auth-be-<name>` module.
- A **no-op fallback** (`NoOpPasswordSyncService`, annotated `@Fallback`) lives in **`t9t-auth-be`** and is used when no other implementation is on the classpath.
- Configuration is read lazily from `ConfigProvider.getConfiguration().getUplinkConfiguration()`, searching for the entry whose `key` matches the constant `OpenBaoPasswordSyncService.OPENBAO_UPLINK_KEY`.
- All methods return a `PasswordSyncStatus` enum value. Callers must inspect the result and surface `ERROR` states as a non-zero return code on the response, which causes the ZK UI to display a popup notification.

## Detailed Implementation Plan

### Task 1 – Configuration: Use Existing `UplinkConfiguration` As-Is

**No changes** to `UplinkConfiguration` or `cfg-be.bon` are required.

The OpenBao connection is identified purely by a **dedicated key constant** defined in `OpenBaoPasswordSyncService` (see Task 3). The existing fields of `UplinkConfiguration` are used as follows:

| Field | OpenBao Usage |
|---|---|
| `key` | Must match the constant defined in `OpenBaoPasswordSyncService` (e.g. `"openbao"`) |
| `url` | OpenBao base URL (e.g. `http://openbao-server:8200`) |
| `token` | OpenBao authentication token (`X-Vault-Token` header) |
| `clientId` | KV v2 mount path (e.g. `"secret"` or `"kv"`) |
| `extraParam` | Optional OpenBao namespace (`X-Vault-Namespace` header) |

- If no `UplinkConfiguration` entry with the matching key is found, the service returns `PasswordSyncStatus.DISABLED` (not `SUCCESS`).
- No new fields, no `openBaoService` boolean flag, no `openBaoKvMount` field.

**Note**: `UplinkConfiguration.java` in `src/generated/` is auto-generated by the Bonaparte DSL and must not be manually edited.

### Task 3 – New Generic Service Interface: `IPasswordSyncService`

**Module**: `t9t-auth-sapi`

#### 3a. Status Enum

**File**: `t9t-auth-sapi/src/main/java/com/arvatosystems/t9t/auth/services/PasswordSyncStatus.java`

```java
package com.arvatosystems.t9t.auth.services;

/**
 * Result of a password synchronization attempt to an external secrets store.
 */
public enum PasswordSyncStatus {
    /** The secret was successfully stored or deleted. */
    SUCCESS,
    /** No password sync backend is configured; operation was skipped intentionally. */
    DISABLED,
    /** The sync attempt failed (network error, auth error, configuration problem, etc.). */
    ERROR
}
```

#### 3b. Interface

**File**: `t9t-auth-sapi/src/main/java/com/arvatosystems/t9t/auth/services/IPasswordSyncService.java`

```java
package com.arvatosystems.t9t.auth.services;

import jakarta.annotation.Nonnull;

/**
 * Generic service for synchronizing user passwords to/from an external secrets store.
 * Implementations may target OpenBao, HashiCorp Vault, AWS Secrets Manager, etc.
 *
 * <p>All methods return a {@link PasswordSyncStatus} to indicate whether the operation
 * succeeded, was intentionally skipped (no backend configured), or failed.
 * Callers are responsible for surfacing {@code ERROR} results to the operator.</p>
 */
public interface IPasswordSyncService {

    /**
     * Writes or updates the password secret for the given userId in the external store.
     *
     * @param userId      the user ID (used as the secret path key)
     * @param tenantId    the tenant ID (used to namespace the secret path)
     * @param password    the plaintext password to store
     * @return {@link PasswordSyncStatus#SUCCESS} if stored successfully,
     *         {@link PasswordSyncStatus#DISABLED} if no backend is configured,
     *         {@link PasswordSyncStatus#ERROR} if the operation failed
     */
    @Nonnull
    PasswordSyncStatus storePassword(@Nonnull String userId, @Nonnull String tenantId, @Nonnull String password);

    /**
     * Deletes the password secret for the given userId from the external store.
     *
     * @param userId      the user ID
     * @param tenantId    the tenant ID
     * @return {@link PasswordSyncStatus#SUCCESS} if deleted successfully,
     *         {@link PasswordSyncStatus#DISABLED} if no backend is configured,
     *         {@link PasswordSyncStatus#ERROR} if the operation failed
     */
    @Nonnull
    PasswordSyncStatus deletePassword(@Nonnull String userId, @Nonnull String tenantId);
}
```

#### 3c. No-Op Fallback Stub

**Module**: `t9t-auth-be`

**File**: `t9t-auth-be/src/main/java/com/arvatosystems/t9t/auth/be/impl/NoOpPasswordSyncService.java`

```java
package com.arvatosystems.t9t.auth.be.impl;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import de.jpaw.dp.Fallback;
import de.jpaw.dp.Singleton;

import com.arvatosystems.t9t.auth.services.IPasswordSyncService;
import com.arvatosystems.t9t.auth.services.PasswordSyncStatus;

/**
 * No-op fallback implementation of {@link IPasswordSyncService}.
 * Used when no password sync backend module (e.g. t9t-auth-be-openbao) is on the classpath.
 * Always returns {@link PasswordSyncStatus#DISABLED}.
 */
@Fallback
@Singleton
public class NoOpPasswordSyncService implements IPasswordSyncService {
    private static final Logger LOGGER = LoggerFactory.getLogger(NoOpPasswordSyncService.class);

    @Override
    public PasswordSyncStatus storePassword(final String userId, final String tenantId, final String password) {
        LOGGER.debug("Password sync is not configured – skipping storePassword for user {}/{}", tenantId, userId);
        return PasswordSyncStatus.DISABLED;
    }

    @Override
    public PasswordSyncStatus deletePassword(final String userId, final String tenantId) {
        LOGGER.debug("Password sync is not configured – skipping deletePassword for user {}/{}", tenantId, userId);
        return PasswordSyncStatus.DISABLED;
    }
}
```

### Task 4 – OpenBao Implementation: New Maven Module `t9t-auth-be-openbao`

Create a new Maven module `t9t-auth-be-openbao` alongside the other `t9t-auth-be-*` modules.

**`t9t-auth-be-openbao/pom.xml`** — declares dependency on `t9t-auth-sapi` and `t9t-cfg-be` (for `ConfigProvider`). No new external library dependencies are required (uses the JDK 11 HTTP client `java.net.http.HttpClient`).

**File**: `t9t-auth-be-openbao/src/main/java/com/arvatosystems/t9t/auth/be/openbao/OpenBaoPasswordSyncService.java`

A **dedicated key constant** is defined inside `OpenBaoPasswordSyncService`:

```java
public static final String OPENBAO_UPLINK_KEY = "openbao";
```

Key responsibilities:
- On first use (lazy initialization), search `ConfigProvider.getConfiguration().getUplinkConfiguration()` for the entry whose `key` equals `OPENBAO_UPLINK_KEY`.
- If **no such entry is found**, both `storePassword` and `deletePassword` return `PasswordSyncStatus.DISABLED` and log at DEBUG level.
- If the entry is found, cache the configuration (URL, token, kvMount from `clientId`, namespace from `extraParam`).
- Use a cached `HttpClient` (JDK 11 `java.net.http.HttpClient`) to communicate with OpenBao.
- Construct the KV v2 API path: `{url}/v1/{clientId}/data/{tenantId}/{userId}`.
- Send the `X-Vault-Token` header using the configured `token` field.
- If `extraParam` is set, send `X-Vault-Namespace: {extraParam}`.
- On any HTTP or IO error, log at **ERROR** level (including the HTTP status code if available) and return `PasswordSyncStatus.ERROR`. Do **not** throw an exception; do **not** let OpenBao failures propagate into the calling transaction.

**OpenBao KV v2 API calls**:

| Operation | HTTP Method | Path |
|---|---|---|
| Write secret | `POST` | `/v1/{clientId}/data/{path}` |
| Delete secret (soft, current version) | `DELETE` | `/v1/{clientId}/data/{path}` |

Request body for write:
```json
{
  "data": {
    "password": "<plaintext password>"
  }
}
```

### Task 5 – Error Propagation: Surfacing Sync Failures as UI Popups

#### Design Decision

Sync failures **must not** be silently swallowed. Any `PasswordSyncStatus.ERROR` result must ultimately reach the operator as a visible popup in the ZK UI.

The t9t framework surfaces non-zero `returnCode` values in `ServiceResponse` as error popups in the ZK UI. The approach is:

1. The sync service returns `PasswordSyncStatus.ERROR` (never throws).
2. The calling service (`PasswordSettingService`, `PasswordChangeService`) or request handler detects `ERROR`.
3. The handler sets a **non-zero return code** on the response (e.g., a new `T9tAuthException.PASSWORD_SYNC_FAILED` constant) **without throwing an exception**, so the main DB transaction is committed normally.
4. The ZK UI receives the non-zero return code and displays a popup with the error message.

> **Important**: Setting a non-zero return code without throwing an exception in a t9t request handler does NOT roll back the transaction. The password change is committed; only the sync failed. This satisfies both requirements: the change succeeds AND the operator is notified.

#### New Error Code

**File**: `t9t-auth-api/src/main/java/com/arvatosystems/t9t/auth/T9tAuthException.java` (or the equivalent `.bon` file that generates it)

Add a new error code constant, e.g.:

```java
public static final int PASSWORD_SYNC_FAILED = AUTH_ERROR_OFFSET + 70;  // choose a free offset
```

With a message like: `"Password was changed successfully, but synchronization to the external secrets store failed. Please check server logs."`

#### Propagation from Services to Handlers

Since `PasswordSettingService` and `PasswordChangeService` run inside the same JPA transaction as the request handler, the simplest propagation path is:

- Both `IPasswordSettingService.setPasswordForUser(RequestContext, ...)` and `IPasswordChangeService.changePassword(...)` are given access to the `IPasswordSyncService` result.
- Option A (**preferred**): The services call `IPasswordSyncService` internally and return the `PasswordSyncStatus` as part of a result record (or as an extended return type), which the request handler checks.
- Option B: The request handler is responsible for calling `IPasswordSyncService` directly after the service call returns.

**Option A details** for `IPasswordSettingService`:

```java
// New result carrier (t9t-auth-sapi)
public record PasswordSettingResult(PasswordEntity passwordEntity, PasswordSyncStatus syncStatus) {}

// Updated interface method signatures
PasswordSettingResult setPasswordForUser(RequestContext ctx, UserEntity user, String newPassword);
PasswordSettingResult setPasswordForUser(Instant now, UserEntity user, String newPassword, Long passwordSetByUserRef);
```

The request handlers that call `setPasswordForUser` inspect `result.syncStatus()` and set `response.setReturnCode(T9tAuthException.PASSWORD_SYNC_FAILED)` when `ERROR` is returned.

### Task 7 – Hook into User Deletion

**File**: `t9t-auth-be/src/main/java/com/arvatosystems/t9t/auth/be/request/UserCrudRequestHandler.java`

Inject `IPasswordSyncService` and call it after a successful hard `DELETE`:

```java
private final IPasswordSyncService passwordSyncService = Jdp.getRequired(IPasswordSyncService.class);

// In execute(...), after the CRUD result is obtained:
if (OperationType.DELETE == crudRequest.getCrud() && result.getReturnCode() == 0) {
    if (Boolean.TRUE.equals(userDto != null ? userDto.getSyncPasswordToOpenBao() : null)) {
        final PasswordSyncStatus syncStatus = passwordSyncService.deletePassword(userDto.getUserId(), ctx.tenantId);
        if (syncStatus == PasswordSyncStatus.ERROR) {
            LOGGER.error("Failed to delete external secrets store entry for deleted user {}/{}", ctx.tenantId, userDto.getUserId());
            result.setReturnCode(T9tAuthException.PASSWORD_SYNC_FAILED);
            result.setErrorDetails("External secrets store entry could not be removed for user: " + userDto.getUserId());
        }
    }
}
```

> **Note**: Only a hard `OperationType.DELETE` triggers secret removal. Deactivating a user (`OperationType.INACTIVATE`) does **not** remove the password from the external store.

## Implementation Notes & Design Decisions

### Module Boundaries

All backend implementation code is placed exclusively in `t9t-auth-*` modules. No changes are made to `t9t-base-be` or any other base-framework module. This keeps the OpenBao integration self-contained within the authentication subsystem.

### Extensibility

`IPasswordSyncService` is intentionally named generically. The `@Fallback` no-op in `t9t-auth-be` ensures the system works without any sync backend. Future implementations (e.g. HashiCorp Vault, AWS Secrets Manager, CyberArk) each go in their own `t9t-auth-be-<name>` module and are activated by adding them to the classpath.

### Error Handling and UI Feedback

Sync failures **must be visible** to the operator. The chosen mechanism — setting a non-zero `returnCode` on the `ServiceResponse` without throwing — ensures:

1. The main DB transaction (password change, user deletion) is committed successfully.
2. The client receives a non-zero return code, which the t9t ZK UI renders as a popup.
3. The server logs contain the full error at ERROR level for diagnostics.

The no-op fallback returns `DISABLED` (not `ERROR`), so unconfigured deployments produce no popups and no log noise.

### Secret Path Convention

The secret path in OpenBao follows: `{clientId}/data/{tenantId}/{userId}`

Example (KV mount `secret`, tenant `DEFAULT`, user `john.doe`): `secret/data/DEFAULT/john.doe`

This namespaces secrets by tenant and user, allowing multi-tenant deployments.

### Token Refresh / AppRole Support

For production use, a short-lived token approach (AppRole auth) is recommended over a static root token. This is deferred to a later work package. In Phase 1, a static token configured in `UplinkConfiguration.token` is used.

### Existing Users Migration

No bulk migration. Existing users with the flag enabled will have their passwords pushed to OpenBao only on the **next password change**.

## OpenBao KV API Reference (v2)

| Operation | Method | URL |
|---|---|---|
| Enable KV v2 | `POST` | `/v1/sys/mounts/{mount}` with `{"type":"kv","options":{"version":"2"}}` |
| Write / update secret | `POST` | `/v1/{mount}/data/{path}` |
| Read secret | `GET` | `/v1/{mount}/data/{path}` |
| List secrets | `LIST` | `/v1/{mount}/metadata/{path}` |
| Soft delete current version | `DELETE` | `/v1/{mount}/data/{path}` |
| Permanently destroy all versions | `DELETE` | `/v1/{mount}/metadata/{path}` |

This integration uses **soft delete** (`DELETE /v1/{mount}/data/{path}`) when a user is removed. The version history and metadata are retained in OpenBao.

Headers required:
- `X-Vault-Token: <token>`
- `Content-Type: application/json`
- (optional) `X-Vault-Namespace: <namespace>`

---

## Resolved Design Decisions

The following questions have been answered and are incorporated into this plan:

1. **KV v1 or v2?** → **KV v2** is used.
2. **Soft delete vs. hard delete on user removal?** → **Soft delete** (`DELETE /v1/{mount}/data/{path}`, deletes the current version only). The metadata and version history are retained in OpenBao.
3. **INACTIVATE triggers delete?** → **No**. Only a hard `OperationType.DELETE` of the user triggers secret removal. Deactivating a user (INACTIVATE) does not remove the password from OpenBao.
4. **Multi-tenant path strategy?** → **Per-tenant namespacing by path** (`{tenantId}/{userId}`). OpenBao namespaces are not used.
5. **Token rotation / AppRole?** → Out of scope for this work package. A static token configured in `UplinkConfiguration.token` is used. Token rotation / AppRole authentication is deferred to a later work package.
6. **Existing users migration?** → No bulk migration. Existing users with the flag enabled will have their passwords pushed to OpenBao only on the **next password change**.
7. **Field name?** → `syncPasswordToOpenBao` is confirmed as the field name.
8. **Where does the service interface live?** → **`t9t-auth-sapi`**. No changes to `t9t-base-be` or any other base module.
9. **Is the interface OpenBao-specific?** → **No**. The interface is named `IPasswordSyncService` and is implementation-agnostic. OpenBao is one possible backend. Future alternatives each get their own `t9t-auth-be-<name>` module.
10. **Silent failure vs. visible error?** → **Visible**. `PasswordSyncStatus.ERROR` results in a non-zero response return code and a UI popup. `DISABLED` (unconfigured) is silent. `SUCCESS` is silent.

## Dependencies

- No new external library dependencies are required for Phase 1 (the JDK 11 HTTP client `java.net.http.HttpClient` is used).
- OpenBao must be reachable from the t9t server at the configured URL.
- OpenBao KV v2 must be enabled at the configured mount path.
- The `t9t-auth-be-openbao` module must be added to the server classpath (e.g. included in the container assembly) to activate the OpenBao backend. Without it, the `@Fallback` no-op is used automatically.
